# Invitation administration and transactional email

Pause transactional-email consumption before applying the community migration, then deploy this compatible API before enabling consumption again. Older workers do not understand the two new kinds and omit the frozen reply address. Keep the compatible worker available until those deliveries are reconciled, including during application rollback. A green migration alone does not establish compatible delivery.

Community event approval and rejection now use the same private transactional outbox. Apply append-only `20261008008000_community_event_email.sql` after the lifecycle and coordinated-deletion migrations. It replaces `private.notify_community_event_status()` and its existing event-status trigger. The decision and delivery reservation commit together; failure to reserve delivery rolls back the decision. This removes the trigger's dependency on the old Supabase `notify-email` endpoint without changing UUID ownership.

Only distinct transitions into published or rejected status for an event with a submitter and stored contact queue mail. Repeated or concurrent updates to the same status reserve one delivery; a later distinct decision can reserve another. Imported events, draft changes, absent contacts and tombstoned recipients do not queue delivery. Approval links use the event UUID at `/events/:id`; rejection links use `/submit-event`. The outbox `target_id` retains the submitter's UUID, while its private payload snapshots the event UUID/title, recipient email and display name. Public/operator delivery listings continue to omit that payload.

These messages run only under the existing `CUTOVER_NOTIFY` installation flag and reuse the serial queue, stable provider key, frozen body and 23-hour retry window. Inline mail also retains optional `RESEND_REPLY_TO`; the first attempt freezes the reply address with the body, so a later configuration change cannot alter a retry. The welcome hosted template remains unchanged. Operator deletion, signed Clerk deletion and direct database deletion cancel and scrub unsent community mail. Revocation checks prevent dispatch after retained-account deletion; historical event attribution and already accepted mail remain intact. An in-flight provider request cannot be recalled and still requires outcome reconciliation.

The paired community migration rollback refuses to run while any community delivery outcome remains in the outbox. Pause dispatch, export and reconcile those rows through the approved private procedure before rollback; it then restores the exact frozen legacy status-notification function and its original kind constraint. Restoring that function reintroduces the Supabase dispatcher dependency. Production migration, provider delivery and rollback remain separately controlled actions.

The app's `/admin/invites` screen uses the existing operator invitation APIs to create and revoke codes and approve or reject requests. Codes are returned in plaintext once; the screen keeps a new code visible until dismissal and reports clipboard failures. Code listings never recover plaintext. Request messages and reviewer notes remain operator-only. Approval creates the existing single-use invitation and pending email reservation. Rejection sends a generic outcome, without private reviewer notes. Invitation settings remain governed by the established database policy.

Apply `20261008004000_transactional_invite_email.sql` before running these API callers. It replaces the private approval/rejection functions' legacy `/functions/v1/notify-email` calls with an outbox insert inside the same decision transaction. Existing public wrappers, invitation validation, outcomes, UUIDs, reservations and audit evidence remain intact. Public API request intake queues one admin notification only when it creates a new pending request. Callback provisioning queues one welcome in the same transaction as a new UUID and trusted mapping. Historical account linking and callback replay do not enqueue another welcome. An outbox failure rolls back its originating decision or provisioning. Clerk deletion cancels and scrubs unsent welcome rows in the deletion transaction, even when dispatch is paused; a request already in flight cannot be recalled.

The private outbox keeps a deduplication key, lifecycle state, lease and attempt history. Only the API service role can access its payload. Pending invitation emails temporarily retain the recipient and plaintext code because the code hash cannot produce the email after a failure. Do not log payloads, provider request bodies or keys. The first provider attempt freezes the sender, recipient, subject, HTML or hosted-template variables. Retries use that exact body and the same `Idempotency-Key`, derived from the outbox UUID. Provider acceptance requires a valid returned email ID. Successful delivery scrubs payload and frozen body; failed or uncertain rows retain them for controlled recovery. Operator HTTP listings return metadata and sanitized failure categories, never email content or plaintext codes.

Resend documents a **24-hour** retention window for idempotency keys in its [official changelog](https://resend.com/changelog/idempotency-keys) and describes the [`Idempotency-Key` HTTP header](https://www.resend.com/blog/engineering-idempotency-keys). Automatic and manual retries stop **23 hours after the first attempt** and move uncertain delivery to `needs_review`. This leaves a margin before provider retention expires. Never create a new key or blindly resend an uncertain row after that window. Reconcile its stable key and provider outcome first. Keep the same Resend account during an uncertain delivery window; rotating to a different account can remove the original deduplication evidence. A provider 409 or 429 can retry within the window; other 4xx responses become failed and require an operator retry after correcting the refusal. A changed frozen payload remains refused by provider idempotency semantics.

The API registers the serial `transactional-email` pg-boss queue and one-minute outbox scan only under existing `CUTOVER_NOTIFY` ownership. Production requires that flag to be explicitly `true`; this implementation does not set it or authorize deployment. This worker owns transactional email only; digest/reminder/notification queues retain their existing owners. Missing `RESEND_API_KEY` leaves rows pending without consuming the uncertain-delivery window. Missing `ADMIN_NOTIFY_EMAIL` likewise keeps admin notices pending. Set `RESEND_FROM` to an approved sender and `APP_URL` to the app's public URL through the separately controlled environment rollout. Welcome uses the existing `family-events-welcome` hosted template with `USERNAME` and `APP_URL`; that template and sender must exist in the configured provider account.

`GET /v1/admin/invite-deliveries` lists the latest 100 metadata records. `/status` reports ownership, provider and admin-recipient configuration booleans. `POST /:id/retry` accepts only an empty body, locks the row, preserves its original body/key/window, records an operator audit and schedules a pending or failed row. It rejects processing, sent, cancelled and reconciliation-required states. Expired pending/failed attempts transition durably to `needs_review` and return 409. A lease claim fences acknowledgments by attempt number, so an older worker cannot overwrite a newer result. `sent` means the provider accepted the email, not that the recipient opened or received it.

Rollback requires pausing the transactional worker and reverting the API request/provisioning callers before applying the paired `_down.sql`. Export unsent private rows through a controlled procedure first; rollback removes the outbox and restores the previous legacy dispatch functions. Preserve recipient/code confidentiality in that export. Do not operate old and new dispatch owners simultaneously. UUIDs, request decisions, invitation counts, reservations and audit rows survive migration rollback. Production migration, callback configuration, provider sender/template validation, delivery reconciliation and the notify ownership cutover remain separate acceptance steps.

Verification uses signed lifecycle HTTP callbacks, actual invitation HTTP operations, owned disposable PostgreSQL, real pg-boss dispatch and stubbed provider HTTP. It covers atomic failure, concurrent approval, callback replay, refusal, retry body/key stability, lost acknowledgment, expired lease owners, absent settings, expiry pause, private-note exclusion, deletion cancellation, access boundaries and migration rollback. These checks send no real email. Authenticated operator browser acceptance still requires controlled Clerk sessions; signed-out browser coverage confirms the route conceals private data.
