# Invitation onboarding

The API owns invitation policy, public requests, and initial member activation. The app's `/onboarding` page requests invitations anonymously, shows verified account setup status, and redeems a code for the signed-in account. Clerk signup redirects there. Creating a Clerk identity alone does not grant invite-only access.

- `GET /v1/onboarding` returns only `{required}` from the existing effective `private.invites_required()` policy. Policy/database failures fail closed.
- `POST /v1/onboarding/requests` accepts only email and an optional message of at most 500 characters. The API normalizes email, serializes requests for that email, and preserves the existing pending-request uniqueness and three-attempts-per-ten-minutes rate policy. A generic receipt avoids disclosing existing requests, review decisions, reviewer identity, or rate history. Repeated requests preserve the message when none is supplied. It never queries or returns private review fields.
- `GET /v1/onboarding/me` requires a verified Clerk bearer and returns `ready`, `invite_required`, `provisioning_pending`, or `access_unavailable` plus the effective policy. A deleted identity is unavailable, rather than pending. No UUID or account email is accepted from or returned to the caller.
- `POST /v1/onboarding/redeem` accepts only a code and requires a verified Clerk bearer. It resolves the trusted mapping explicitly outside the enabled-access guard. Account features still require enabled, unexpired access through the existing global guards.

Redemption locks the Clerk identity, verified mapped email, retained auth row, and access row in the lifecycle lock order. The existing `public.redeem_invite_for_email` operation supplies hashed-code validation, code-row serialization, pending reservation behavior, and the five-failed-attempts-per-five-minutes limit. The API claims that reservation, enables initial member access, and writes one `user.invite_redeem` audit in the same transaction. Ready accounts return ready without consuming another code. An initial account must have no prior enabled timestamp, disabled timestamp, disabled reason, expiration, or claimed reservation. Disabled, expired, operator, and previously claimed accounts cannot enroll again. Audit failures roll back the claim, code count, and access. Invalid-code attempts commit their rate evidence before returning 400.

The frozen invite tables/helpers and API Clerk lifecycle migration must exist. API-owned admin request delivery additionally requires `20261008004000_transactional_invite_email.sql`. Rollback is the application rollback; it preserves UUIDs, claims, request rows, access, and audits.

Public request intake avoids the legacy `request_invite` dispatcher. New pending requests enqueue API-owned admin notification in the same transaction; repeated pending requests update their message without duplicate delivery. Requests remain visible to the operator invitation API. See [transactional invitation email](TRANSACTIONAL_INVITATION_EMAIL.md) for delivery states and gated provider rollout. Local fixture acceptance does not establish production delivery.

HTTP/PostgreSQL tests cover anonymous intake/privacy, trusted mapping, pending provisioning, deleted identities, invalid/expired/exhausted/revoked codes, account revocation, code races, replay, rate limits, and audit rollback. With the app built, set `ONBOARDING_BROWSER_APP_DIR` to its checkout and run the onboarding integration test against a disposable database to add desktop/mobile browser request coverage through app → API → PostgreSQL. Set `PLAYWRIGHT_BROWSERS_PATH` only when reusing an existing browser installation. Authenticated browser signup, callback provisioning, and redemption still require controlled Clerk browser sessions; HTTP fixtures do not establish that release acceptance. No production writes, provider configuration, or real messages are part of these checks.
