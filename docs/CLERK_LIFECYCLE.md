# Clerk lifecycle and retained UUIDs

The API owns `POST /webhooks/clerk`. The app's existing `/api/webhooks/clerk` URL can forward the exact request body and `svix-id`, `svix-timestamp`, and `svix-signature` headers to it. Forward the API response status and body. Never acknowledge a callback before the API applies it. Configuring the provider endpoint or forwarding route is a separate rollout step; this document does not establish deployment.

Set `CLERK_WEBHOOK_SIGNING_SECRET` and `CLERK_SECRET_KEY` on the API. Missing signing configuration returns 503; invalid or expired signatures and invalid lifecycle identities return 400. Unsupported signed event types are acknowledged without mutation. Database/provider failures return 503 for retry. An ownership conflict returns 409 and requires operator reconciliation.

For `user.created` and `user.updated`, the API reads the current Clerk user through the Backend API. It uses only that user's verified primary email, never callback email fields, unsafe metadata, or a client-selected UUID. Existing mappings keep their UUID and role. New mappings may link only one confirmed historical `auth.users` email; ambiguous, unconfirmed, already linked, or deleted historical accounts fail closed. Database profile roles determine historical operator links. New accounts are members even if provider metadata claims an operator role.

New UUID records use the existing `private.invites_required()` policy. Open registration enables access. Invite-only registration creates disabled access unless a live, unclaimed pending invitation is consumed in the same transaction. Callbacks never overwrite established access, expiry, preferences, or chosen display names. Mapping/profile email updates use monotonically newer provider snapshots. Concurrent callbacks serialize account and email binding.

Apply `schema/migrations/20261008001000_clerk_lifecycle.sql` through the API migration runner before enabling callbacks. The private lifecycle ledger retains provider version and deletion tombstones independently of cascaded account rows. A deletion trigger also tombstones existing mappings when the legacy database admin operation deletes a UUID. Clerk-origin UUID insertion retains profile/access initialization but skips the old welcome-email dispatcher. Ticket #44 must implement supported API-owned welcome delivery alongside transactional invitation email. Welcome delivery is still open; it must not silently depend on the old backend.

`user.deleted`, or an authoritative Clerk 404, permanently tombstones the Clerk ID. Ordinary account cleanup uses the established `auth.users` cascades and retains one `user.delete` audit snapshot. If an attribution foreign key prevents hard deletion, the API retains the historical UUID/evidence, removes the mapping, disables access, and records `cleanup_deferred: true`. Old Clerk JWTs then fail mapping authorization. Duplicate or stale callbacks cannot recreate access, and another Clerk ID cannot claim retained deleted storage. Ticket #43 owns further coordinated personal-data cleanup for retained accounts.

Rollback requires disabling callback delivery/forwarding first. The paired `_down.sql` restores the previous profile initialization function and removes lifecycle objects without retyping UUIDs or changing mappings. Export tombstones and deferred-cleanup records before rollback and restore them before re-enabling lifecycle handling; dropping the ledger removes replay protection. Do not execute rollback against production without its separately approved procedure.

Acceptance tests use signed HTTP deliveries, fixture-backed Clerk reads/token verification, and a disposable production-shaped PostgreSQL catalog. They cover historical ownership/preferences, verified email policy, role boundaries, invitation races, duplicates/stale snapshots, provider failures, deletion races, attributed operator revocation, retained audits, and migration rollback. They do not contact Clerk, deliver messages, or prove production webhook configuration.
